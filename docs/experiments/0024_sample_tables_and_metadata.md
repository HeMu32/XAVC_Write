## Original Read Worker

The callback pointer stored at ELF relocation 0x301ba8 resolves to worker
0x115df8 in the original libmpr. Its read-side sequence is:

1. Movie presentation information: 0x228170.
2. Video descriptors: 0x226d20.
3. Audio descriptors: 0x228bf0.
4. Metadata descriptors: 0x22843c.
5. Out-of-band parameter-set preparation: 0x11075c.
6. Actual file reading through the worker's ring-buffer/list path.

Later, 0x114894 consumes the queued descriptors and 0x10d7d8 builds
decoder-facing information tables. Hardware buffer transfer/submission
is a further stage, not covered by this execution.

All addresses in this document are ELF VMAs. Ghidra adds 0x100000.
Exports/logs: `analysis/decompile-mpr/`,
`analysis/ghidra-read-loop-0024.log`,
`analysis/ghidra-sample-preflight-0024.log`,
`analysis/ghidra-sdk-samples-0024.log`.

`emulate_xavc_reader.py` now follows the original worker's distinction
between per-chunk queries and a completed presentation window. It resets
descriptor flags/counts for each query as the original worker does.
It does not advance the presentation window on every video chunk.

## Independent Sample Index

The guest-generated records are checked against the separate
`sony_mp4` ISO BMFF parser, not against fields generated by the emulator.

- Video sample number, file offset and size must match the source index.
- Metadata offset and size must match an indexed metadata sample.
- Audio ranges must lie inside source PCM chunks and be sample aligned.
- Aggregate descriptor byte counts must match their individual rows.
- Video sample numbers must be unique and ordered.
- If the original getter reports video end, every source video frame
  must have been covered, not merely an initial subset.

C6509: **all 90 frames pass**, with three original video queries:
30 frames/flags 2, 30/flags 3, 30/flags 19. The first two queries belong
to one presentation window. End-of-video coverage is verified.
Evidence: `analysis/xavc-samples-C6509-0024.json`.

C0007: **the first 240 of 14,170 frames pass** in eight queries.
This is not a whole-file descriptor traversal.
Evidence: `analysis/xavc-samples-C0007-0024.json`.

## SPS/PPS And Video Decode Tables

The new probe runs original out-of-band buffer/list constructors and
0x11075c. The resulting parameter-set bytes are compared with AVCC's
actual length-delimited SPS/PPS arrays; no parameter bytes are normalized.

It then runs original video configuration-table builder 0x10c998 and
frame-table builder 0x10c4a4. Frame sizes and timestamp fields must match
the SDK descriptors from which the tables were constructed.

C6509's first 30 video descriptors successfully produce 31 entries:
one configuration entry and 30 frame entries. Its one SPS and two PPS
records match the source AVCC byte-for-byte.
Evidence: `analysis/xavc-tables-C6509-0024.json`;
the independent conversion checks are also exercised by the tests.

C6510's selected **I-only mode** successfully retrieves the first video
sample, extracts matching parameter sets and builds matching decode
tables. Evidence: `analysis/xavc-tables-C6510-ionly-0024.json`.
This is one selected sample in mode 1, not normal continuous playback.
There is no audio descriptor coverage in that mode.

The parameter-set arrays and frame table records are real output from
original routines. The ring buffer uses bounded guest memory and
single-thread lock models. No hardware stream submission is performed.
Mutex initialization/locking and printf are explicit modeled services,
not evidence about actual concurrency or a camera error trace.

## RTMD Parsing And Metadata Tables

The probe constructs the original RTMetadatSmplDatParser and TCUBConv,
then runs query-mode transition, the basic timecode-item query, and
metadata table builder 0x10c550 on selected source packets.

C6509 frames 0, 1 and 89, and C6510 frames 0, 1 and 1533, return success
from the original parser transition and contain the requested timecode
item. Their metadata table conversions return zero.
Evidence: `analysis/xavc-rtmd-C6509-0024.json`,
`analysis/xavc-rtmd-C6510-0024.json`.
These selected packets are not complete per-frame metadata coverage.

Important negative control: an empty packet can still receive a zero
outer table-conversion result and one default table entry even though
the requested timecode item is absent. Accordingly, the tool records
the nested query status, item-presence flag and output separately.
A zero outer status alone does not qualify metadata parsing.

Native and minimal EDIUS metadata need not store their basic timecode
bytes in the same part of the extended item. The direct byte comparison
in the test applies to the known minimal EDIUS packet, not to arbitrary
native metadata. Original TCUB conversion handles the native form.

## Budgeted Normal-Mode Probes

Normal-mode presentation queries are expensive in instruction-by-
instruction emulation. The tool now has a wall-time budget, active-call
record, guest registers, selected original-entry traces, and completed
partial batches on failure. A timeout is recorded as an emulator
`TimeoutError`, not an original firmware status or media rejection.

Matched 20-second probes for C0007 and C6510 both exhaust the budget in
the first presentation query. Both show the same audio-track timestamp/
sample-info traversal making progress around audio sample 0x5b48.
This timeout therefore does not discriminate these two inputs.

Evidence:
`analysis/xavc-presentation-C0007-bounded-0024.json`,
`analysis/xavc-presentation-C6510-bounded-0024.json`.
The function trace labels are analyst descriptions of original entries,
not claims that the full camera call context has been captured.

An earlier unbudgeted full Cat traversal was stopped without touching
the card; it produced no complete report and is not acceptance evidence.
`analysis/xavc-reader-C6509-combined-0024.json` passes the complete
90-frame descriptor/conversion checks but later times out in a separate
metadata probe. Its overall selected-check result is correctly false;
the successful sub-results must not be presented as whole-probe success.

## Remaining Boundary

No root cause is established. These results extend original-code
coverage beyond MP4 opening, but do not clear every metadata sample,
normal-mode traversal of C6510, hardware transfer/decoder submission,
or the physical playback failure path. Neither nominal bitrate nor one
metadata field is promoted to the explanation.

The next investigation remains the actual post-table submission and
error callback path, with the user-confirmed 7M4 as the target.
No additional card patch follows from a budget expiry.
