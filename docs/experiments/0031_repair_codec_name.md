# 实验0031：修复数据库时消失的片段与XML格式名称

调查及定点修正：2026-11-13至2026-11-14，SD卡F盘，ILCE-7M4。
本次不研究CFexpress，也不改变编码参数或重新编码画面。

## 结论与边界

已用实际卡快照、原生片段、固件调用路径和原厂代码的正反对照确认：
生成器把H.264数值等级40拼成了Sony XML名称`HP@L40`，而正确名称是`HP@L4`。
C6520、C6521的MP4读取本来成功，但XML基本信息读取返回状态3。
仅在内存中改正这个名称，该读取过程即成功。

这解释了本轮数据库修复为何撤掉这两段的记录，**不是低码率画面不能解码的证据**。
C6522还有另一项独立问题：29.97p时，容器两份4M声明被原厂MP4属性查询拒绝。
两个调用都可能返回数字3，但不是同一个检查，也不能仅凭相同状态码归因。

用户随后明确授权修改卡上的C6520、C6521。两段按此结论准备并执行定点修正；
写入、读回、快照与最终审计单独记录。2026-11-14用户明确反馈
**C6520、C6521现在能被机身列出**，记录在`analysis/camera-observations-0031-result.json`。
当时播放、缩略图、音频、跳转及再次修复数据库后是否保留未单独确认；
不能把该次列出扩大为这些结果。后续0033另有修复后的磁盘编录证据，见文末。

## 1. 修复前后实际改变了什么

修复前：`backup/snap_20261113T180914`。
修复后：`backup/snap_20261113T221317`，77份元数据、153项媒体清单，零错误。
完整差异：`analysis/0031-repair-snapshot-diff.json`。
重新核验快照完整性、当前卡和七个相关MP4的证据：
`analysis/0031-repair-evidence-v2.json`。

- 只有`PRIVATE/DATABASE/DATABASE.BIN`发生变化，共302字节，文件长度未变。
- 旁路XML、MEDIAPRO和其他元数据全部哈希一致。
- 所有媒体文件的成员、大小、修改时间均未改变；这不是全卡媒体内容哈希。
- 对C6501、C6519、C6520至C6524另做完整SHA-256，均匹配工作区保留原件。
- 视频记录数57变54，撤掉119、120、121号记录，分别对应C6520、C6521、C6522。
- 同时增加三条支持记录，所以活动记录总数仍是121。总数相同不等于视频没有减少。
- MEDIAPRO仍有57个Material，没有删除这三段的XML条目。磁盘文件也仍在。

用户明确报告C6520、C6521不列出；C6522修复后未被单独报告界面状态。
其数据库记录被撤掉是读卡发现，不冒充用户观察。

数据库还完成了C6519、C6523、C6524的稀疏记录。C6523引用已有25M/59.94属性，
C6524引用新建的4M/59.94属性。这与用户报告两段修复后仍能播放相符，
不能据此假定29.97p的所有声明也都可接受。

## 2. 原生片段与固件不是只有一条线索

原生C6501：1920×1080、29.97p、16M、High 4.0。
它的XML使用`AVC_1920_1080_HP@L4`，修复后记录仍在。
保存原件为`analysis/C6501-reference-0028.MP4`，旁路XML在修复后快照内。

固件为`firmware/m4-v602/usr/lib/libmpr.so`：
SHA-256 `1a7a8007828810f948eb4fb95b9a269176355553a69977f6d8f2ae59516f5532`。
下列地址是ELF虚拟地址；现有Ghidra导出地址在其基础上加`0x100000`。

| ELF地址 | 已识别作用 |
|---|---|
| `0x8cff4` | 初始化XML枚举名称，包括HP的L4、L41、L42等 |
| `0x24bf44` | 名称查找；L4返回`0x4c`，未知L40返回`0x9a` |
| `0x23d394` | VideoFrame属性检查；未知编码名导致返回8 |
| `0x253e8c` | 载入XML，外层返回0不保证每个节点都语义有效 |
| `0x2543fc` | 提取XML基本信息；本案错误名称导致返回3 |
| `0xde530` | `GetRecordInfoFromNrtMeta`，读取MP4内嵌XML并传播错误 |
| `0xde778` | `GetRecordInfo`，先读MP4属性，再读XML基本信息 |
| `0xb9340` | `RepairM4Inconsistencies`，稀疏记录检查失败进入`sidb::Delete`路径 |

这里读取的是**MP4内嵌XML**，所以只改旁路XML不足以修正这一检查。
观察到的Delete是撤掉数据库记录，本轮没有删除MP4文件。
没有执行完整的可写固件修复过程；其控制流来自反编译，实际撤记录来自卡快照。

## 3. 完整XML读取的交叉对照

`tools/emulate_nrt_semantics.py`执行原始AArch64代码和原始Expat，
初始化实际的XML结构和枚举表，再调用原厂载入、基本信息、标记数量和状态方法。
对照只在内存中改变一个名称，不改MP4、码流、音频或存储卡。

| 文件/对照 | XML名称 | 载入 | 基本信息 |
|---|---|---:|---:|
| C6519原文件 | L41 | 0 | 0 |
| C6519仅把名称改为L40 | L40 | 0 | 3 |
| C6520原文件，视频16M | L40 | 0 | 3 |
| C6520仅把名称改为L4 | L4 | 0 | 0 |
| C6521原文件，视频4M、容器声明16M | L40 | 0 | 3 |
| C6521仅把名称改为L4 | L4 | 0 | 0 |

成功行的标记数量、片段状态读取也都返回0；原始可执行代码逐段核对未改变。
原厂节点检查中，L40确实返回8，名称查找返回未知枚举；不是按字符串有无猜测。
正反对照原始报告为`analysis/0031-nrt-*.json`，最终审计绑定六份完整对照。

仿真显式建模标准C++字符串、经典C地区设置的字符分类/排序、整数输入和
十进制输出流，以及分配器和部分C运行库。不替换Sony名称查找、节点校验、
基本信息读取或错误判断。遇到未建模依赖、越界、超时即报告仿真错误。
前期`model*`、`attempt*`报告中的这些错误保留，但不计作相机拒绝证据。

## 4. 之前验证为什么没有发现

`SonyProfile.video_codec`曾直接使用数值`level_idc=40`生成字符串`L40`。
验证器又用同一属性当作期望值，因此双方一致地接受了错误名称。
此前“XML检查通过”只证明与生成规则一致，没有证明Sony能接受其语义。
这是本项目验证覆盖的缺口，不是相机硬件或用户操作的问题。

现在：

- 生成器把完整整数等级的名称写成L4；数值H.264等级仍然是40，不改SPS等级。
- 新增独立的`sony_nrt_codec.py`，采用固件中的字面名称，不复用字符串拼接规则。
- 生成文件、旁路XML与MEDIAPRO校验均拒绝L40。
- 写卡验证schema升为6，要求独立名称检查；旧报告不得继续用于部署。
- 约176秒的0030待写文件也有旧名称，已标记阻止部署，历史文件和报告没有覆盖。
- `analysis/0031-regression-final.log`：300项测试通过，包括运行库模型、
  原厂名称查找、错误名称反例、旧准入报告拒绝和定点修正负对照。

## 5. 经授权的定点修正与编录恢复

开始修改前再做快照：`backup/snap_20261114T001050`。
历史稀疏描述仅从`backup/snap_20261113T135135`提取，路径和支持依赖必须与
当前数据库逐字节相同。分配始终来自当前快照，**没有回写任何历史整库**。

每段只处理四个文件：

1. `PRIVATE/M4ROOT/CLIP/C6520.MP4`或`C6521.MP4`的内嵌XML区域。
2. 对应`C6520M01.XML`或`C6521M01.XML`。
3. `PRIVATE/M4ROOT/MEDIAPRO.XML`中该Material的`videoType`属性。
4. `PRIVATE/DATABASE/DATABASE.BIN`，重新新增该编号的稀疏记录及必要头部计数/校验。

内嵌XML将L40缩为L4后，在文档末尾补一个合法空白，保持XML盒长度。
旁路XML保持与其逐字节一致。整个`mdat`、整个`moov`、所有轨道载荷、
盒边界、采样表和偏移都与保留原件相同。没有重新编码，也没有改动
SPS、PPS、图像数据、PCM、逐帧附加信息、PROF、UMID、创建时间或缩略图。
MEDIAPRO只改目标属性，不重新序列化其他节点或更新其创建时间。

C6520先写入，读回并制作`backup/snap_20261114T002148`；
C6521随后基于这一新快照准备和写入。数据库分别新分配127、128号记录，
没有重启用旧119、120号槽位。现有活动记录及其支持记录保持原字节。
两次操作共修改六个不同文件，不新增或删除任何卡文件。
C6522原有错误声明和文件保持不动，不借本次修正扩大修改范围。

操作工具：`tools/repair_clip_codec_0031.py`。它只允许C6520、C6521，
默认只准备本地文件；`--apply`必须绑定修正文件的原厂XML和MP4读取报告。
写前重新核验快照，写后逐项读回并快照；出错停止，不自动恢复旧数据库。

每段本地材料及写卡日志：
`output/repair-0031/C6520/`、`output/repair-0031/C6521/`。
修正后文件还执行了原厂MP4属性、采样、参数集、解码表和首/次/末逐帧附加信息
检查；采样检查为30/767帧，不冒充全片硬件解码。
媒体数据未变的依据是完整载荷相等，而非只检查这30帧。

最终合并审计：`analysis/0031-repair-final-audit.json`。
修正后的卡上文件、记录、写前写后快照与七个相关MP4哈希以该报告为准。

## 6. 实机验证

最新用户原文：“C6520、C6521现在能被相机列出.”
此为列出恢复的直接实机证据，绑定上次已读回的修正文件，不追改旧准备/写卡审计。
该反馈本身没有说明是否再次执行过数据库修复。

剩余验证：缩略图是否正常、能否开始及完整播放、音频和跳转；
再次执行“修复影像数据库”后确认两段是否仍然列出。

为下一份长片段写入而捕获的新快照`backup/snap_20261114T005737`显示：
C6520/21记录仍为原来的127/128，未改变；DATABASE另新增C6522稀疏记录129，
其余元数据与媒体清单未变。仅记录这一差异，不将其解释成C6522已能播放，
也不推断用户执行过再次修复。见`analysis/0032-reconnected-card-diff.json`。

修正前可播放不代表修复后仍被编录；原厂软件读取成功也不代替上述机身观察。
本次没有据此宣称普遍最低码率或所有H.264缓冲字段的必要性。
